# 会话凭证准备指南

> 适用于 `--full` 完整历史模式。主包只**消费**凭证；可选的实验性获取实现
> 单独放在 `extras/collect_session.py`，默认不参与主流程。
> 本文档定义需要什么、怎么验证、失败时怎么办。准备工作在本人设备上完成。
>
> 这份文档的价值主要在第 4 节：**已经实测走不通的路径清单**。
> 新版客户端改版后，网上流传的很多老办法已经失效，照着做只会白折腾。

---

## 1. 前置条件

| 条件 | 说明 |
|---|---|
| 系统 | 桌面端微信 4.x（Windows 上验证过；其它平台未验证） |
| 登录态 | 客户端已登录本人账号 |
| 目标公众号 | 已在客户端里打开过该号的主页或任意一篇文章 |
| 时效 | 会话参数通常只有几小时有效，过期需重新准备 |

---

## 2. 需要的参数

客户端在打开公众号内容时，会在自己发出的请求里带上这些参数：

| 参数 | 形态 | 备注 |
|---|---|---|
| `__biz` | base64 串 | 公众号标识，可从任意一篇该号文章 URL 里拿到 |
| `uin` | URL 编码的 base64 | 账号标识 |
| `key` | 长十六进制串 | 会话密钥，最容易过期 |
| `pass_ticket` | URL 编码串 | 与 `key` 成套 |
| `appmsg_token` | 长串 | 常被**双重** URL 编码 |
| `wxtoken` | 通常 `777` | 可留空，代码会补默认值 |

把它们存成本地 JSON（格式见仓库根目录 `credentials.example.json`），
或放进环境变量 `WECHAT_BIZ_CREDENTIALS`。**不要提交、不要写进日志、不要留在仓库目录里。**

支持一次给多组，程序会逐组试探：

```json
{
  "credentials": [
    { "uin": "...", "key": "...", "pass_ticket": "...", "appmsg_token": "..." },
    { "uin": "...", "key": "...", "pass_ticket": "...", "appmsg_token": "..." }
  ]
}
```

## 3. 决策树

```
开始
 ├─ 有现成文章清单？── 是 ──> 直接用 csv / chatlog 输入源，不必准备凭证
 │
 └─ 需要全量历史
     ├─ 运行 extras/collect_session.py 收集若干组会话参数（或按本文自行实现）
     ├─ 逐组请求 action=getmsg&f=json&offset=0
     │    ├─ ret = 0            → 有效，进入自动翻页
     │    ├─ ret = -3 no session → 该组过期/不匹配，试下一组
     │    └─ 其它 ret            → 先检查第 5 节的编码问题
     ├─ 全部失效 → 在客户端里重新打开该号主页，重新收集
     └─ 仍拿不到 → 降级到 csv / chatlog / sogou，不要卡在这一步
```

`history.probe()` 已经实现了「逐组试探」，你只需要把候选组交给它。

## 4. 已验证不可行的路径（别再试了）

这些是 2026-11 在微信 4.x 桌面端实测的结论，能省掉大量无效尝试：

| 尝试 | 实际结果 |
|---|---|
| 浏览器打开 `profile_ext?action=home` | 「请在微信客户端打开链接」——该地址只在客户端会话里渲染 |
| 在客户端里打开该链接再找「复制链接」 | **新版会重建成原生资料页**（`全部/贴图/文章/视频号`），不是网页，菜单里没有复制链接，也没有历史页按钮 |
| 找「查看历史消息」按钮 | 手机端与电脑端 4.x 均已移除，历史图文并进资料页消息流 |
| `action=getmsg&f=json` 不带凭证 | `{"ret":-3,"errmsg":"no session"}` |
| 搜狗微信的 `/link?url=...` 跳转 | 302 到 `antispider`，触发验证码 |
| 搜狗 `tsn=5&ft=&et=` 自定义时间范围 / `usip` 参数 | 返回空结果，参数无效 |
| `appmsgalbum?action=getalbum` 不带 `album_id` | 「该内容已暂停访问」；带真实 `album_id` 反而能打开合集页 |
| `mp/homepage` | 「签名错误」 |
| Wechat2RSS 等第三方镜像 | 多数小号未收录，返回 404 |
| CDP / 调试端口接管内置浏览器 | 客户端 WebView 进程未开 `--remote-debugging-port`；常见的 9222 端口属于别的 Electron 应用，与微信无关 |
| 翻本机缓存目录找实时凭证 | `cache` / `temp` / `resource` / `business` / 客户端资源目录里只有 JS 代码中的字样，没有实时参数；参数只存在于运行时 |
| 不带 `key` 直接抓文章页 | 返回「未知错误，请稍后再试」——**这不是出口 IP 被风控，是缺登录态**；补齐参数后本机请求正常 |

## 5. 参数编码陷阱

踩过一次就会记很久：

- `appmsg_token` 在运行时请求里常见 `%252B` 这类**双重编码**，需要解码两次；
  `uin` / `pass_ticket` 通常只需一次（`%3D%3D` → `==`）。
- `__biz` 是 base64，末尾的 `==` 在 URL 里要编码成 `%3D%3D`，但拼参数时别重复编码。
- `wxtoken` 留空时补 `777`，`x5=0`、`f=json` 别漏。
- 请求需要带客户端自己的 User-Agent（`MicroMessenger/... WindowsWechat ...`）。

`history.normalize_credentials()` 已经处理了这些，传入原始值即可。

---

## 6. 有效性探测与自动翻页

- **探测**：逐组请求 `offset=0`，只认 `ret: 0`。实测 12 组候选里可能只有 1 组有效，
  所以「多收集几组」比「反复调一组」有效得多。
- **翻页**：用响应里的 `next_offset` 递增，不要自己按 `count` 硬加；
  直到 `can_msg_continue=0` 为止。实测一个 300 多篇的号约 31 页。
- **解析**：`general_msg_list` 是**字符串形式的 JSON**，要二次解析；
  每次群发可能是多图文，正文在 `multi_app_msg_item_list` 里，别只取第一条。
- **链接**：`content_url` 里的 `\/` 和 `&amp;` 要还原，否则打不开。

这些在 `history.py` 里都实现了，此节只是方便你排查。

## 7. 两种省力做法

**直接用实验性助手**（推荐）：`extras/collect_session.py` 已实现第 3 节的收集、去重、
编码兼容与逐组有效性探测，且不打印参数内容。

```bash
python extras/collect_session.py --self-test          # 只测解析，不碰进程
python extras/collect_session.py --biz <__biz>        # 收集并验证
```

**或者交给 AI agent**：如果你用 AI agent 操作本机，可以直接把下面这段发给它：

> 我在本机 Windows 上已登录微信 4.x 桌面端。请帮我为 `wechat-biz-archive` 的
> `--full` 模式准备会话凭证：阅读本仓库 `docs/SESSION_PROVIDER.md`，按第 4 节避开
> 已验证不可行的路径，从本机客户端运行时收集 `uin / key / pass_ticket / appmsg_token`
> 的若干组候选值，按第 5 节处理编码，写入本机临时 JSON（不要写进仓库目录、不要提交、
> 不要输出凭证内容到对话里），然后用 `history.probe()` 验证哪组有效。
> 全部失败就明确告诉我，不要伪造数据。

这样「能不能折腾出来」取决于 agent 的本机操作能力，而不是仓库里有没有那段实现。

---

## 8. 边界

- 仅限**本人设备、本人账号**，用于整理自己能访问到的公开内容。
- 遵守对应平台的服务条款；不要高频批量请求，不要商业分发他人内容。
- 凭证是临时会话参数，不是账号密码，也不要把它当作可长期保存的资产。
- 本仓库不抓取、不存储、不分发文章正文，只处理标题 / 日期 / 链接等元信息。
